## 1. 项目背景与目标

### 1.1 背景

在微服务架构中，各业务服务普遍存在敏感数据加解密需求：数据库字段加密、接口传输加密、配置文件敏感信息加密等。如果每个服务各自实现加解密逻辑，会导致密钥分散管理、算法实现不一致、缺乏统一的密钥轮转和审计能力。

旧版 KMS（base-kms）已实现核心功能并稳定运行，但存在以下不足：
- 强依赖公司内部框架（bajcommon-parent、bajcommon-*）
- 使用 Dubbo 协议，需注册中心，接入门槛高
- 使用 Fastjson（历史安全漏洞）
- 仅支持 MySQL，无法轻量化部署
- 仅支持 Redis 缓存，无降级方案
- 无独立管理后台前端

### 1.2 目标

构建一个**纯净、轻量、可独立部署**的密钥管理系统：

| 能力 | 说明 |
|------|------|
| 密钥全生命周期管理 | 生成、存储、分发、轮转、销毁 |
| 多算法支持 | AES / SM4（对称）、RSA / SM2（非对称）、签名、摘要 |
| 多租户隔离 | 按应用组隔离密钥，支持跨应用密钥授权 |
| 安全接入 | 应用注册 + 签名鉴权 + 频率限制 |
| 密钥版本管理 | 同一别名支持多版本，平滑轮转 |
| 审计追踪 | 完整的操作日志和加解密记录 |
| 纯净独立 | 零公司内部框架依赖，开箱即用 |
| 数据库无关 | 同时支持 MySQL 和 SQLite |
| 缓存降级 | Redis 可选，无 Redis 自动降级为 Caffeine 本地缓存 |

### 1.3 迭代规划

**一期（已完成）** — KMS 基本功能：
- 租户入驻，根据租户和应用创建唯一密钥
- 审计日志记录，对操作和接口请求进行记录存储
- 自动加签，客户端自动完成加签，服务端自动验签
- 公钥获取、数据加解密、密钥轮换
- 页面操作权限功能，根据角色分配对应的页面菜单操作权限

**二期（已完成）** — KMS 功能完善：
- 应用权限控制，可根据应用做不同的应用访问权限控制
- 提供加解密 Starter，更方便接入和使用
- 密钥授权机制，支持跨服务解密
- 账户独立权限，各账户数据隔离
- 应用访问限制，基于 Redis Lua 脚本的令牌桶限流

**三期（V2.0 新版）** — 技术栈升级：
- Java 8 → Java 17，Spring Boot 2.7
- Dubbo → HTTP REST
- Fastjson → Jackson
- 新增 SQLite 支持
- 新增 Caffeine 本地缓存降级
- 新增 Vue 3 管理后台

### 2.2 模块划分

```
pcm-kms/
├── pcm-kms-common          # 公共模块：常量、枚举、异常、工具类
├── pcm-kms-core            # 核心模块：加密引擎、策略实现
├── pcm-kms-server          # 服务端：API + Service + DAO + Filter 链
├── pcm-kms-client-starter  # 客户端 SDK（Spring Boot Starter）
├── pcm-kms-admin-ui        # 管理后台前端（Vue 3）
└── sql/                    # 数据库初始化脚本
```

### 2.3 调用流程

```
业务方调用加解密流程：

1. 业务应用引入 pcm-kms-client-starter
2. 配置 clientId + clientSecret（应用入驻时获得）
3. 调用方式一：注解式
   - @KmsEncryptField / @KmsDecryptField：DO 字段自动加解密
   - @KmsMethod / @KmsParam：方法级加解密
4. 调用方式二：编程式
   - KmsClient.encrypt(plainText, alias)
   - KmsClient.decrypt(cipherText, alias)
5. SDK 自动完成签名 → HTTP 请求 → KMS Server
6. KMS Server Filter 链：验签 → 限流 → 获取客户端信息 → 业务处理 → 日志
7. 返回结果
```

### 3.2 核心概念

| 概念 | 说明 |
|------|------|
| **ClientInfo（应用信息）** | 需要加解密服务的微服务，通过 clientId + 签名密钥鉴权 |
| **ClientGroup（应用组）** | 同一业务域下应用的分组，同组内密钥互通 |
| **Alias（别名）** | 密钥的业务别名，如 `user-phone-encrypt`，业务方通过别名加解密 |
| **KeyVersion（密钥版本）** | 同一别名下可有多个版本，解密时指定版本，加密默认最新版本 |
| **SecretId（密钥ID）** | 密钥材料的唯一标识，与 KeyMaterial 一一对应 |
| **ClientAuthorization（密钥授权）** | A 服务授权给 B 服务，B 可在有效期内解密 A 的加密数据（单向） |
| **UserClientGroup（用户应用组关联）** | 管理员通过应用组映射查看对应应用数据；普通用户只能看自己创建的应用 |

## 4. 详细设计

### 4.1 租户入驻

租户入驻有两个步骤：创建租户应用和应用启用。

**创建租户应用**：根据以下字段生成应用信息（默认禁用状态）：
- tenant_code（租户编码）
- client_name（应用名称）
- client_group（应用分组，同服务发布的项目名称，如 iam、base）
- contacts（联系人）
- mobile（手机号）
- job_no（工号）
- client_id（应用ID，使用 spring.application.name）

**启用租户应用**：启用后自动生成密钥信息：
- public_key（公钥，页面可见）
- private_key（私钥，不可见，加密存储）
- secret_key（密钥，不可见，加密存储）
- secret_id（密钥ID，提供给应用系统配置）
- algorithm（加密算法）
- crypto_type（加密类型）
- key_purpose（密钥用途）
- alias（别名，应用ID下的唯一值，和密钥ID对应）
- key_version（密钥版本，默认为 1，每次变更 +1）

### 4.2 应用操作

| 操作 | 说明 |
|------|------|
| 更新 | 修改应用基本信息 |
| 启用/禁用 | 控制应用是否可用 |
| 删除 | 逻辑删除应用及对应的密钥信息 |
| 查看 | 查看非敏感的元数据信息 |

### 4.3 密钥管理

- 查看应用ID、别名、公钥信息，更新密钥相关信息
- 密钥轮换：定期新增密钥信息，变更公钥/私钥/密钥，别名不变，新版本 +1
- 日志清理：定期清理审计日志，防止日志数据过多影响性能

### 4.4 自动加签校验

客户端 Filter 拦截实现：
- 客户端只需在配置文件配置客户信息（private_key、tenant_code）
- 调用者调用接口无需每次手动添加签名
- 客户端自动加签，服务端自动验签，确保安全性

新版（V2.0）改为 HTTP REST 方式：
- 客户端通过 HMAC-SHA256 签名
- 签名算法：`sign = HMAC-SHA256(clientSecret, body + timestamp + nonce)`
- 服务端验证时间戳（防重放，默认 5 分钟窗口）
- 验证 nonce（Redis 去重，无 Redis 时用本地 LRU 缓存）

### 4.5 日志记录

- **后台管理服务**：通过 AOP 切面记录用户操作信息
- **加解密服务**：通过 Filter 记录业务方调用接口信息（不记录请求和响应参数）
- 服务端自动对所有请求进行日志记录保存，包括调用失败异常记录
- 服务端对实现方法进行统一异常处理，返回统一响应实体

### 4.6 公钥获取

业务系统根据别名获取公钥，如果该别名在应用不存在，则自动新增该别名。

### 4.7 数据加解密

| 接口 | 说明 |
|------|------|
| 申请公钥 | 根据别名获取最新的公钥信息 |
| 非对称解密 | 根据别名 + 密文，查询最新 private_key 解密返回明文 |
| AES 加密 | 根据别名 + 明文进行数据加密，返回别名、密文、版本信息 |
| AES 解密 | 根据别名、密文、版本进行解密，返回明文信息 |
| 默认算法 | 不选择算法时默认使用 AES |

### 4.8 密钥授权

**背景**：存在多个业务方数据互通的情况，但又不属于各自服务，需要对应用密钥进行授权，支持跨服务解密。

**原逻辑**：通过 client_group 来对各应用进行互通加解密，但存在局限性——不同应用组之间不互通。

**改造后**：新增 `kms_client_authorization` 表：
- grantor_client（授权方应用ID）
- grantee_client（被授权方应用ID）
- secret_id（密钥ID）
- permission_type（权限类型：ENCRYPT/DECRYPT）
- valid_start / valid_end（有效期）
- authorization_status（授权状态：0-失效 1-生效）

> 注意：这是单向授权。若双方都互相可以解密，请配置 2 次。授权有效期默认 1 年。

### 4.9 账户独立权限

**背景**：为了保证安全，使各个账户独立并且互不影响。

**设计**：
- 管理员：通过 `sys_user_client_group` 表与应用组映射，可查看对应应用组下所有应用数据
- 普通用户：只能查看自己创建的应用数据
- 用户登录时查询关联映射表，有映射则按应用组过滤，无映射则按当前用户账号过滤

### 4.10 应用访问限制

**背景**：为了保证服务稳定可靠，防止大量调用导致服务不可用。

**方案**：参考高德地图 API 处理，分为每分钟调用限制和每天调用限制，利用 Redis Lua 脚本确保原子性。

| 统计维度 | 存储结构 | 刷新机制 | 默认值 |
|----------|----------|----------|--------|
| 每日限额 | Redis key: 固定前缀+clientId+年月日，value: 计数器 | 每日 00:00 自动重置 | 1,000,000 |
| 分钟限额 | Redis key: 固定前缀+clientId+年月日时分，value: 计数器 | 每分钟自动重置 | 1,000 |

**实现步骤**：
1. 启动项目加载策略到内部缓存
2. 定时加载数据库策略更新到内部缓存
3. 页面添加/更新同步更新缓存和数据库

### 4.11 定时任务

| 任务 | 说明 |
|------|------|
| 密钥轮换 | 根据配置的轮换周期定期更换每个租户应用下的密钥信息，旧密钥保留，新版本 +1 |
| 日志清理 | 根据配置的日志保留天数定期清理日志信息，物理删除 |

### 4.12 操作权限

- 前端根据用户登录后得到的权限进行显示/隐藏菜单按钮
- 后端根据当前用户配置的角色菜单权限进行控制
- 若用户所属角色无权限，则提示对应信息

## 5. 数据库设计

### 5.1 表重命名（V2.0 规范化）

| 旧表名 | 新表名 | 说明 |
|--------|--------|------|
| kms_key_base | kms_key_material | 密钥材料表 |

### 5.2 应用信息表

```sql
CREATE TABLE kms_client_info (
  id            INT          NOT NULL AUTO_INCREMENT COMMENT '主键',
  client_id     VARCHAR(255) NOT NULL COMMENT '应用唯一标识',
  tenant_code   VARCHAR(255) NOT NULL COMMENT '租户',
  client_name   VARCHAR(255) NOT NULL COMMENT '应用名称',
  secret_id     VARCHAR(255) DEFAULT NULL COMMENT '签名的密钥ID',
  enabled       TINYINT      NOT NULL DEFAULT '0' COMMENT '应用启用状态',
  client_group  VARCHAR(255) DEFAULT NULL COMMENT '应用分组',
  contacts      VARCHAR(255) DEFAULT NULL COMMENT '联系人',
  job_no        VARCHAR(32)  DEFAULT NULL COMMENT '联系人工号',
  mobile        VARCHAR(32)  DEFAULT NULL COMMENT '联系人手机号',
  create_time   DATETIME     DEFAULT NULL COMMENT '创建时间',
  modify_time   DATETIME     DEFAULT NULL COMMENT '更新时间',
  modifier_user VARCHAR(50)  DEFAULT NULL COMMENT '更新人',
  creator_user  VARCHAR(50)  DEFAULT NULL COMMENT '创建人',
  deleted       BIGINT       DEFAULT NULL COMMENT '删除',
  PRIMARY KEY (id),
  KEY idx_client_id (client_id) USING BTREE COMMENT '应用id'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='应用信息列表';
```

### 5.3 密钥材料表

```sql
CREATE TABLE kms_key_material (
```

## 6. 安全设计

### 6.1 密钥存储安全

- 所有存储在 `kms_key_material` 中的密钥材料（private_key、secret_key）均使用 MasterKey 二次加密
- MasterKey 通过环境变量注入，不存储在数据库中
- 内存中的密钥使用后立即清零

### 6.2 传输安全

- 生产环境强制 HTTPS
- 请求签名防篡改和重放（HMAC-SHA256）
- 敏感接口响应中的密钥材料不返回（private_key 仅创建时返回一次）

### 6.3 访问控制

- 三层隔离：应用组 → 应用 → 密钥别名
- 管理后台：基于角色的访问控制（RBAC），管理员拥有所有权限，普通用户只有部分权限
- 开放 API：基于 clientId + 签名 + 密钥绑定
- 账户独立：管理员通过应用组映射查看数据，普通用户只看自己创建的数据

| **配置中心** | 依赖 Luffy 配置中心 | 本地配置文件 + 环境变量 |
| **SDK 接入** | Dubbo 协议 + 复杂 Filter 链 | HTTP REST + 简洁
