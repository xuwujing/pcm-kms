# PCM-KMS 开发进度周期说明

版本：v1.1  
日期：2026-06-10

## 1. 总体策略

PCM-KMS 应按阶段推进，不适合一开始就做成“全能力终态项目”。

建议采用以下节奏：

1. 先完成可运行骨架
2. 再完成核心 KMS 闭环
3. 再优化接入体验
4. 最后补稳定性和扩展项

整个计划以这三个结果为导向：

- 一个能本地直接跑起来的 KMS
- 一个能被业务服务轻松接入的 KMS
- 一个你半年后再看也不会觉得太重的 KMS

## 2. 阶段总览

| 阶段 | 周期建议 | 目标 |
| --- | --- | --- |
| Phase 1 | 第 1-2 周 | 项目骨架和本地可运行 |
| Phase 2 | 第 3-4 周 | 核心 KMS 能力闭环 |
| Phase 3 | 第 5-6 周 | 管理台和 Starter 接入可用 |
| Phase 4 | 第 7-9 周 | 稳定性、安全性、运维能力增强 |
| Phase 5 | 第 10-12 周 | 文档、测试、发布准备 |

## 3. 分阶段说明

### Phase 1：本地可运行

目标：

- 后端启动成功
- 前端启动成功
- SQLite 模式可直接运行
- Redis 缺失时仍然可运行

交付项：

- Maven 多模块骨架
- Spring Boot 2.7 基础工程
- Vue 3 + Vite 管理台骨架
- MySQL / SQLite 配置切换
- Redis / 本地缓存切换
- 统一响应、统一异常、基础日志

验收标准：

- 新机器只依赖 JDK、Maven、Node 即可启动最小模式

### Phase 2：核心 KMS 闭环

目标：

- 真正具备 KMS 的基础使用价值

交付项：

- 租户管理
- 应用创建
- 应用启用后自动生成接入密钥材料
- 密钥创建 / 查询 / 轮转
- AES / SM4 加解密
- RSA / SM2 加解密
- 签名 / 验签
- 公钥按别名获取
- 审计日志

验收标准：

- 能完成“创建应用 -> 启用应用 -> 获取接入信息 -> 调用加解密接口”

### Phase 3：接入体验可用

目标：

- 让业务方可以低成本接入

交付项：

- `pcm-kms-client-starter`
- 编程式加解密 API
- 注解式加解密增强
- 管理台核心页面
- 应用与密钥绑定页面
- 审计日志查询页面

验收标准：

- 一个 demo 服务能在 30 分钟内完成接入
- 业务方不需要手工处理签名细节

### Phase 4：稳定性增强

目标：

- 从“能用”提升到“更适合长期使用”

交付项：

- 日级和分钟级限流
- nonce 防重放
- 管理员权限模型
- 指标采集
- Docker / Docker Compose
- 日志定时清理

验收标准：

- Redis 和本地缓存两种模式都可稳定工作
- 限流和防重放机制可验证

### Phase 5：发布准备

目标：

- 形成可持续维护的标准仓库

交付项：

- README
- 快速接入文档
- 架构说明文档
- 多智能体协作开发说明
- 测试计划和基础测试

验收标准：

- 新人按文档能独立跑起项目
- 多个开发者或智能体能按统一规则接力开发

## 5. 优先级建议

### P0

- 本地启动
- 核心密钥管理
- 核心加解密能力
- 应用启用与接入材料生成
- Starter 最小接入能力
- 审计日志

### P1

- 管理台完整度
- 限流和防重放
- 指标和 Docker

### P2

- 密钥导入导出
- 更复杂权限模型
- Gateway / Nacos 强化集成

## 6. 风险与控制

### 风险 1：再次做重

现象：

- 一开始就拆太多服务
- 一开始就引入过多中间件

控制策略：

- 第一阶段只允许单体可运行方案作为主路径

### 风险 2：Starter 过度侵入

现象：

- 业务系统不得不重构大量代码

控制策略：

- 显式 API 优先
- 注解增强作为可选项

### 风险 3：双数据库兼容复杂度过高

控制策略：

- 用 Flyway 管理脚本
- 尽量把兼容逻辑收敛到基础设施层

## 7. 最终建议

这个项目最应该先交付的不是“更多能力”，而是“更稳的主路径”。

主路径必须足够清晰：

- 本地启动简单
- 接入简单
- 文档简单

只要主路径稳定，后续规划能力才能逐步叠加。
